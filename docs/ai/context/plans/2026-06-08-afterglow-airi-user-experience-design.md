# AIRI + Afterglow 用户体验设计

> Date: 2026-06-08
> Status: Draft
> Owner: Codex
> Track: Afterglow continuity UX / AIRI integration polish

## 1. 问题定义

当前链路已经证明两件事：

- Afterglow 风格的记忆检索可以命中导入聊天记录
- 命中的上下文已经会影响最终回复

但当前体验里还存在一个明显偏差：

- 用户会看到类似“我从导入记忆里找到了相关上下文：...”这样的解释型回复

这不符合 Afterglow 的产品定位，也不符合 AIRI 的集成边界。

## 2. 目标

把 Afterglow 在 AIRI 中呈现为“关系连续性与生活状态的大脑”，而不是“把检索过程讲给用户听的 RAG 助手”。

用户应该感觉到：

- 她记得你们之间的关系
- 她的语气延续了过去
- 她像在自然接话，而不是展示命中的记忆片段
- 她可能有延迟、沉默、分条、生活状态变化，但这些都像角色行为，不像系统提示

## 3. 设计原则

### 3.1 用户只看到角色，不看到检索机制

禁止把以下内容直接暴露在用户回复中：

- “我检索到了记忆”
- “我从向量数据库找到了上下文”
- “我参考了导入聊天记录”
- “我命中了历史片段”
- 原样转述命中的样例作为解释

记忆命中只应该改变回复的：

- 语气
- 称呼
- 关系温度
- 接梗方式
- 是否短句
- 是否自然延续过去的互动节奏

### 3.2 Afterglow 提供连续性，AIRI 负责产品呈现

Afterglow 在 AIRI 里的职责是：

- 提供关系相关的回复倾向
- 提供命中的记忆提示
- 提供延迟、沉默、分条、生活状态等策略信号

AIRI 在前台负责：

- 呈现消息
- 控制节奏
- 显示等待、沉默、残留状态
- 决定哪些内部信号能被用户感知，哪些必须隐藏

### 3.3 记忆要“溶进回复”，不能“贴在回复外面”

理想状态下，用户输入一句：

- `啵啵爱你`

如果记忆中存在高相关、且风格上成立的回应，最终应该表现为自然续写，比如：

- `好嘟`
- `亲亲`
- `怎么突然这么乖`
- `你今天怎么这么甜`

而不是：

- `我从导入记忆里找到了相关上下文：user:好嘟！ | assistant:亲亲贝贝右脸蛋！`

### 3.4 体验设计不能脱离 Afterglow 的检索方法

这个设计不是单纯的文案约束，还必须建立在 Afterglow 既有检索结构之上。

根据上游实现，Afterglow 不是“只拿一段相似文本塞进 prompt”这么简单，而是依赖：

- 三索引混合检索
- 五路召回
- RRF 融合
- 关系记忆
- life 状态
- live memory 持续回写
- LanceDB 本地向量库

所以 AIRI 侧的集成设计必须遵守一个前提：

- 不能只复刻“像 Afterglow 一样说话”的表层效果
- 必须尊重 Afterglow 的检索结构与向量记忆结构
- 否则最后得到的会是“有 Afterglow 名字的普通 prompt 包装器”

## 4. 回复层级

Afterglow 命中记忆后，回复构成优先级应为：

1. 当前用户输入的真实语义
2. 当前生活状态 / 时段 / 可用性
3. 关系记忆与长期 persona
4. 命中的真实历史回复风格样例
5. AIRI 的分条、延迟、舞台呈现策略

其中第 4 层的作用是“塑形”，不是“引用展示”。

## 5. Afterglow 方法约束

### 5.1 三索引不是可选装饰，而是核心语义来源

上游文档和实现都明确了三索引混合检索：

- `response_pairs`：用户输入 -> 对方回复样本
- `friend_messages` / `friend_examples`：单条对方消息
- `dialogue_windows`：多轮上下文窗口

这三类索引承担的是不同语义职责：

- `response_pairs` 决定“这句话以前对方通常怎么回”
- `friend_examples` 决定“这个人平时怎么说话”
- `dialogue_windows` 决定“类似场景下上下文是怎样展开的”

因此 AIRI 集成时不能把它们粗暴压成一个“memory snippets”概念。

### 5.2 五路召回必须保留语义分层

Afterglow 上游把主检索描述为“五路向量召回 + relationship_memory + life”。

在 AIRI 集成约束里，应至少保留这些分层概念：

1. `response_pairs`
2. `friend_examples`
3. `dialogue_windows`
4. `live_messages` 的语义召回 / recent live
5. query rewrite / 多变体检索产生的并行召回结果
6. `relationship_memory`
7. `life`

这里的重点不是要求 AIRI 前端重写完整检索器，而是：

- 不要把 Afterglow 当成“只有一个最终文本回复”的黑盒
- 要承认它最终回复的质量来自这些分层共同作用
- 观测、调试、验收时要检查这些层是否真的在发挥作用

### 5.3 向量数据库必须是产品能力的一部分，不只是导入仓库

Afterglow 上游的向量库不是一次性导入后就静止不动的附件，而是持续参与运行时链路：

- 导入聊天记录后写入 LanceDB
- 检索时从 LanceDB 做混合召回
- 每轮对话可异步回写 `live_messages`
- 可选让 `ai_generated` 低权重参与长期连续性

因此 AIRI 侧的设计约束应为：

- 不能把“导入成功”当成唯一完成标准
- 必须验证导入后的向量库在真实聊天回合里持续参与检索
- 必须区分 `human_original`、`live`、`ai_generated`、`relationship_memory`
- 必须避免把全部长期记忆都退化成前端本地 prompt 拼接

### 5.4 检索融合方式要与上游精神一致

Afterglow 上游当前明确使用：

- RRF 融合
- recency 权重
- warmth boost
- source trust 分层
- 可选 cross-encoder 粗排
- 可选 LLM rerank

这意味着 AIRI 在接入 Afterglow 时，不应该：

- 在前端追加一个自定义“简化版相似度排序”覆盖掉它
- 只取某一类检索结果就断言“命中了记忆”
- 用页面观测结果替代真实检索链路判断

更合理的方式是：

- 尊重上游给出的最终回复与策略信号
- 在需要调试时，额外观测命中的来源类型和融合结果
- 但不把这些中间过程泄露给普通用户

## 7. 浏览器实操验收方法

这一链路的验收必须以真实浏览器操作为准，不能只依赖单元测试、接口直调或本地日志推断。

### 7.1 验收前置条件

- AIRI 前端运行在真实页面，例如 `http://localhost:5173/`
- Afterglow 后端已启动
- 已在 AIRI 设置中把聊天服务来源切到 `Afterglow`
- 已完成聊天记录导入，且 `/memory/stats` 返回非零索引数量

### 7.2 真实浏览器操作步骤

1. 打开 AIRI 首页
2. 在设置页确认：
   - 当前聊天提供商是 `Afterglow`
   - 当前聊天模型是 `afterglow-companion`
3. 回到首页聊天区
4. 点击底部“说点什么...”输入框
5. 手动输入一条能够命中已导入历史的消息，例如 `啵啵爱你`
6. 直接按回车发送
7. 观察页面是否出现自然回复，而不是：
   - 空回复
   - `404`
   - `Remote sent ...`
   - “我从记忆里找到了相关上下文”

### 7.3 同步观测项

在真实浏览器发送同时，需要同步检查：

- Afterglow 后端日志里是否出现实际聊天请求
  - `POST /chat/completions` 或 `POST /v1/chat/completions`
- `/debug/stats` 是否记录到本轮模型调用
- `/memory/search` 对同一 query 是否能命中 `response_pairs`、`friend_examples`、`dialogue_windows`

### 7.4 通过标准

以下条件同时满足，才算真正通过：

- 用户在真实浏览器完成发送
- Afterglow 后端真实收到聊天请求
- 最终回复是自然角色回复，不暴露检索过程
- 调试数据能证明命中的向量记忆确实参与了生成链路

### 7.5 失败信号与定位顺序

如果失败，按以下顺序定位：

1. 页面有没有真正触发发送
2. 前端把请求发到了哪个路径
3. Afterglow 后端有没有收到请求
4. 收到请求后是否进入检索与模型链路
5. 回复文本是否暴露了内部检索元信息

## 6. 用户可见行为规范

### 5.1 正常命中

当历史里有明确相似互动时：

- 回复应自然缩短
- 优先复用真实称呼与语气节奏
- 可以保留暧昧、玩笑、亲密度，但必须由历史与当前输入共同支撑

### 5.2 证据不足

当命中弱或上下文不足时：

- 不要强行装得很熟
- 不要硬贴亲密表达
- 应退回轻量自然回复

### 5.3 不该出现的元信息

绝不向用户显示：

- 检索命中数
- 召回片段原文列表
- prompt 拼接结果
- provider 名称
- model 名称
- “记忆库 / 向量库 / prompt / system”字样

这些信息只允许出现在：

- devtools
- 调试报告
- 诊断日志
- 开发者专用观测页面

## 7. 实现与验收要求

### 7.1 体验验收之外，还要做方法验收

除了“回复像不像真人”之外，还要验证实现是否仍然符合 Afterglow 方法本身。

至少要检查：

- 导入后的数据是否真正进入向量库
- 聊天时是否确实发生了基于向量库的检索
- `response_pairs`、`friend_examples`、`dialogue_windows` 是否都有机会影响结果
- `relationship_memory` 与 `life` 是否仍然参与决策
- live memory 回写是否正常
- 若开启 `AI_GENERATED_LONG_TERM_ENABLED`，其权重是否仍然低于真人原始语料

### 7.2 报告层必须能说明“体验正确”与“方法正确”

后续所有联调报告建议同时回答两类问题：

体验问题：

- 最终回复是否自然
- 是否泄露了内部检索机制
- 是否符合角色关系与语气

方法问题：

- 当前回合用了哪个 provider / model
- 是否命中向量库
- 命中的主要来源更接近 `response_pairs`、`friend_examples` 还是 `dialogue_windows`
- 是否经过 relationship memory / life / live memory 共同作用
- 当前行为是否仍符合 Afterglow 的五维方法与 LanceDB 运行模式

## 8. 调试与正式体验边界

为了验证链路，开发阶段允许存在：

- debug query 参数触发自动发消息
- prompt projection 观测
- provider / model / message 状态日志

但这些能力必须满足：

- 默认不向普通聊天界面暴露
- 不在主对话区、输入区附近常驻显示
- 不污染用户看到的角色回复内容

调试信息应该进入独立承载面：

- devtools 页面
- 专门的上下文观测页
- 浏览器控制台
- 可显式开启的开发面板

而不是用户聊天画面左下角的常驻黑色日志块。

## 9. 实现建议

### 7.1 后端 / Provider 层

- 使用命中的记忆片段作为 style/example/context 注入
- 不把命中的原文包装成“我找到记忆了”的回答
- 对 mock / fallback backend 做明显区分，避免把演示文案误判成正式行为
- 尽量保留 Afterglow 原有的检索分层，而不是在 AIRI 内另起一套简化 memory 拼接

### 7.2 AIRI 编排层

- 把 Afterglow 输出区分为“用户可见正文”和“内部策略信号”
- 延迟、沉默、life markers、schedule hints 这类内部协议必须继续剥离
- continuity payload 应转成 AIRI-native signals，不把 provider 原始叙述直接外泄
- 若要做可观测性，优先观测来源类型、命中路径、策略信号，不要把检索样例直接变成回复正文

### 7.3 前端层

- 主聊天页只展示角色可见内容
- 调试面板默认移除
- 需要调试时走专门 devtools 页面或显式开发入口

## 10. 验收标准

认为体验达标时，应满足：

- 用户发送一句短句时，回复像真实角色接话，而不是像 RAG 助手解释来源
- 命中导入记忆后，回复能体现关系连续性
- 用户界面中不再出现黑色常驻调试日志块
- 调试信息仍然可通过开发工具和专用观测入口获取
- AIRI 仍然像 AIRI，Afterglow 仍然像上游连续性引擎，而不是反过来
- 检索与记忆链路仍然符合 Afterglow 的三索引 / 五路召回 / LanceDB 持久化思路，而不是被前端简化逻辑替代

## 11. 浏览器实测方法

以下测试方法优先级高于“只看代码”或“只看控制台日志”。

原因：

- 这个链路同时跨越导入页、provider 配置页、聊天页、前端编排、Afterglow 后端和向量库
- 仅看单点日志，很容易把 mock、fallback、旧状态或界面假象误判成真实链路
- 真实浏览器操作更接近最终用户的使用路径

### 11.1 测试原则

- 必须从浏览器真实打开 AIRI 页面开始
- 必须通过真实输入框发送消息
- 必须观察聊天页面上的最终用户可见结果
- 必须同时记录 provider / model / prompt 观测信息
- 必须区分“命中了记忆”和“回复样式正确”这两个维度

### 11.2 测试前置条件

开始测试前确认：

- Afterglow provider 已配置且可连通
- 已完成聊天记录导入
- 向量库非空
- 当前会话使用的是 `afterglow` provider
- 已知至少 1 到 3 条容易命中的测试短句
- 浏览器端实际已经拿到 `AFTERGLOW_*` 配置，而不是只有本地 `.env.local` 文件里存在值

建议准备两类测试语料：

- 强命中短句：例如曾经高频出现、回复模式明确的短句
- 弱命中短句：例如泛化问候、上下文依赖较强的话

### 11.3 浏览器端主流程

1. 打开聊天主页，而不是只停留在设置页
2. 确认当前 provider 为 `afterglow`
3. 先去 provider 或 memory 页面确认：
   - base URL 是否为预期值
   - API key 是否已保存
   - 默认 model 是否与本地配置一致
4. 在真实输入框中点击聚焦
5. 手动输入测试消息
6. 通过回车或发送按钮发送
7. 等待回复完成
8. 记录最终展示给用户的消息内容
9. 再检查开发观测信息，确认这轮是否真的走了 Afterglow 链路

### 11.3.1 浏览器配置注入检查

这一步必须放在正式聊天测试前，否则很容易把“本地配置文件存在”误判成“浏览器运行时已生效”。

检查顺序：

1. 打开设置页，确认页面展示的 Afterglow base URL / default model 是否与 `.env.local` 一致
2. 如果页面展示为空、默认值不对，优先怀疑前端 env 注入失败，而不是先怀疑后端
3. 修改 `.env.local` 后，重新启动或刷新对应前端开发服务，再重新打开页面确认
4. 如果浏览器里选中了 Afterglow，但页面展示的 base URL / model 仍然停留在旧值，说明当前前端 bundle 没有拿到最新 env

这次联调里已经实际出现过：

- `.env.local` 中存在 `AFTERGLOW_API_KEY`
- `.env.local` 中存在 `AFTERGLOW_BASE_URL`
- `.env.local` 中存在 `AFTERGLOW_MODEL`
- 但前端运行时没有暴露 `AFTERGLOW_*`

所以后续浏览器测试时，应把“前端是否真正注入 env”列为必查项，而不是只看本地文件内容。

### 11.4 必测场景

#### 场景 A：导入后基本命中验证

目标：

- 验证导入聊天记录后，向量库确实能影响正常对话

操作：

- 发送一条明确能在历史中命中的短句
- 观察回复是否出现关系连续性和历史语气

通过标准：

- 回复内容明显受历史语气影响
- 回复不是通用助手式回答
- 回复没有泄露“我检索到了记忆”这类内部过程

#### 场景 B：弱命中退化验证

目标：

- 验证证据不足时不会硬装熟

操作：

- 发送一条历史中不稳定、或泛化程度较高的短句

通过标准：

- 回复仍自然
- 不强行输出高亲密度内容

### 11.5 浏览器实操验收步骤

为了避免“代码看起来对了，但真实页面链路没通”，每次验收都应按下面顺序执行。

1. 打开 `http://localhost:5173/settings/memory`
2. 点击“检查 Afterglow 服务”
3. 记录页面状态区的这些字段：
   - 服务连接
   - 导入身份
   - 后端 persona 配置
   - 后端配置向导
   - 当前聊天 provider
   - 当前聊天 model
4. 如果“服务连接”不是“已就绪”，停止聊天验收，先修连通性
5. 如果“后端配置向导”不是“已就绪”，停止聊天验收，先修真实 Afterglow 的 chat / embedding / auth 配置
6. 选择真实聊天文件并点击“识别聊天文件”
7. 确认：
   - 没有出现后端 `list has no attribute get` 这类格式错误
   - 如果是训练集 `conversations` JSON，页面应出现“已转换为 Afterglow 可导入格式”或等价提示
8. 补齐 self / friend 的名字与 UID
9. 点击“启动导入”
10. 等待页面出现导入任务状态，并记录：
   - task id
   - task status
   - task progress
11. 导入完成后，重新点击“检查 Afterglow 服务”
12. 确认：
   - `friend_messages` 大于 0
   - `response_pairs` 大于 0
   - `relationship_memories` 有合理值
   - `persona 卡片` 为“已就绪”或有明确生成中的解释
13. 回到 `http://localhost:5173/`
14. 点击底部输入框，输入真实测试短句并发送
15. 记录用户可见回复，不允许只记录控制台日志
16. 再结合日志补充：
   - 用户发了什么
   - AIRI 发给 Afterglow 的 provider / model
   - 拼接了哪些 prompt 段
   - 最终 prompt 是什么
   - Afterglow 是否命中向量记忆
   - 是否出现内部机制泄露

### 11.5.2 基于本次联调经验的浏览器失败恢复方式

这次联调里，浏览器实操已经暴露出一些非常具体的问题，后续测试建议直接按这个恢复顺序处理。

#### A. 页面看起来有配置，但服务检查仍失败

优先怀疑：

- 页面里保存的是旧 token
- 本地 `.env.local` 里的值不等于真实 Afterglow 实例当前需要的值
- 真实 Afterglow 服务换过实例或重启过，token 已变化

恢复顺序：

1. 先用真实接口验证 `config/ping`
2. 再用同一个 token 验证 `config/status`
3. 只有 `config/status` 授权成功，页面里的 key 才能认为有效

#### B. 页面状态看起来快对了，但“后端配置向导”仍未完成

优先怀疑：

- AIRI 本地保存了字段
- 但还没成功通过 `putConfigValues()` 写入真实 Afterglow

恢复顺序：

1. 检查 Memory 页里的“Afterglow 真实上游模型”各字段是否都非空
2. 再检查导入前是否已经真正触发配置同步
3. 若 `wizard_completed` 仍为 `false`，禁止继续把当前状态当作“可导入”

#### C. 浏览器自动化读重页面超时

这不是产品链路成功与否的证据，只是调试方式不稳。

处理原则：

1. 不把“大页面快照超时”误判成产品失败
2. 优先做小范围检查：
   - 只读取 URL
   - 只读取状态按钮是否存在
   - 只读取一小段可见文本
3. 避免把“跳转 + 整页快照 + 大文本提取”放在同一步
4. 真实验收时仍以页面可见结果为准，而不是以自动化快照是否成功为准

#### D. 页面已经选中 Afterglow，但回合不一定真的走 Afterglow

恢复顺序：

1. 发送前记录页面状态里的当前 provider / model
2. 发送后结合日志确认 provider 调用链
3. 如果 provider / model 与预期不一致，这一轮归类为“链路失败”

### 11.6 浏览器验收失败时的判定规则

当浏览器里出现“看起来配置好了”的假象时，优先按以下顺序排查：

1. 页面本地是否只是保存了 URL 和 API key
2. `config/status` 是否真的通过鉴权
3. `wizard_completed` 是否真的为 `true`
4. `v1/info` 和 `memory/stats` 是否来自同一个真实 Afterglow 实例
5. 页面状态文案是否把“本地已填写”误显示成“远端已连接”

如果第 2 到 4 步不能同时成立，就不能把当前结果算作“Afterglow 已正常工作”。
- 不出现硬贴历史样例的情况

#### 场景 C：provider 实际生效验证

目标：

- 验证页面不是看起来选中了 Afterglow，但实际走了别的 provider

操作：

- 在发送前后记录 active provider / active model
- 对照聊天回合结果和观测状态

通过标准：

- 当前回合实际 provider 为 `afterglow`
- model 与 Afterglow 配置一致
- 回复时序与 Afterglow 链路相符

#### 场景 D：记忆命中但用户不可见内部机制

目标：

- 验证“方法生效”和“体验正确”同时成立

操作：

- 发送一条强命中短句
- 确认开发观测里能看出这轮与记忆有关
- 再确认用户看到的回复没有暴露任何内部术语

通过标准：

- 观测层能证明记忆参与了生成
- 用户层只看到自然回复

### 11.5 浏览器实测时建议同时记录的证据

每轮测试建议记录以下证据：

- 测试时间
- 页面 URL
- 当前 provider
- 当前 model
- 用户发送内容
- 最终回复内容
- prompt projection 关键信息
- 是否命中记忆
- 是否出现不应有的元解释

如果需要形成报告，建议按下面结构整理：

- `输入`
- `页面可见回复`
- `provider / model`
- `prompt 观测`
- `记忆是否参与`
- `是否符合 Afterglow 体验设计`

### 11.5.3 建议记录的实际操作日志

为了让后续报告可以准确回答“你发送了什么、拼接了哪些 prompt、最终 prompt 是什么、回复是什么、Afterglow 是否正常运行了”，每次浏览器实操建议至少记录：

1. 页面操作日志

   - 是否真的出现了消息气泡
2. Afterglow 状态日志
   - `config/status`
   - `v1/info`
   - `memory/stats`
   - 导入 task 状态

### 11.5.4 本次项目建议采用的真实浏览器测试脚本

下面这套脚本不是抽象流程，而是结合这次联调里已经踩过的坑整理出来的“实际点页面”方法。

#### 阶段 0：确认当前实例不是旧状态假象

1. 打开 `http://localhost:5173/settings/memory`
2. 先看页面里是否存在下面这些输入项：
   - `Afterglow Base URL`
   - `配置向导 Token`
   - `运行时 API Key`
   - `我是谁`
   - `对方是谁`
3. 如果这几个输入项都不存在，优先判定为：
   - 当前前端 bundle 不是最新代码
   - 或页面没有刷新到新版本
4. 这时不要继续导入或发消息，先刷新页面或重启前端开发服务

#### 阶段 1：先验证“配置向导链”和“运行时链”是两条不同链

这一步必须实际在页面上操作，不要只看本地配置文件。

1. 在 `配置向导 Token` 中填写当前 Afterglow 启动后打印出来的 setup token
2. 在 `运行时 API Key` 中填写当前 Afterglow 的 `XUWEN_API_KEY`
3. 点击“检查 Afterglow 服务”
4. 重点记录页面状态区是否分别显示：
   - `运行时 API`
   - `配置向导`
5. 成功口径：
   - `运行时 API` 为已就绪
   - `配置向导` 为已就绪
6. 失败口径：
   - 只有一个已就绪，另一个没就绪
   - 或者两个状态混在一起，无法区分

这一步的意义是防止把“真实运行时 key”和“配置向导 token”误当成同一个东西。

#### 阶段 2：先做空库检查，再决定是否可以导入

1. 仍在 `settings/memory` 页面，点击“检查 Afterglow 服务”
2. 记录状态区中的：
   - `后端 persona 配置`
   - `后端配置向导`
   - `friend_messages`
   - `response_pairs`
   - `relationship_memories`
3. 如果页面显示：
   - `后端配置向导：未完成`
   - `friend_messages = 0`
   - `response_pairs = 0`
4. 则本轮测试只能判定为：
   - Afterglow 服务能访问
   - 但真实记忆链路还没有准备好
5. 这时禁止直接跳到聊天首页做“命中记忆”结论

#### 阶段 3：补齐真实 Afterglow 向导配置

如果第 2 阶段发现 `wizard_completed` 没完成，必须继续在同一页补齐这些字段：

1. `我是谁`
2. `对方是谁`
3. `我的 UID`
4. `对方 UID`
5. `聊天上游 Base URL`
6. `聊天上游 API Key`
7. `聊天上游 Model`
8. `Embedding Base URL`
9. `Embedding API Key`
10. `Embedding Model`
11. `Embedding 维度`

页面上如果提供：

- `复用当前 AIRI 聊天 provider`
- `复制选中 provider 配置`

可以先点这些按钮减少手工输入，但点完之后仍然必须再点一次“检查 Afterglow 服务”。

通过标准：

- `后端配置向导` 变为已就绪
- `后端 persona 配置` 变为已就绪，或者页面明确说明正在生成且可继续

#### 阶段 4：真实导入聊天文件

1. 在 `settings/memory` 页面选择真实文件：
   - `~/Downloads/example-chat_train.json`
2. 点击“识别聊天文件”
3. 若文件是训练集 `conversations` JSON，页面应出现类似：
   - `已转换为 Afterglow 可导入格式`
4. 如果页面出现的仍是原始后端错误，例如：
   - `list has no attribute get`
5. 则判定桥接逻辑未生效，本轮停止
6. 补齐页面要求的 self / friend 字段后点击“启动导入”
7. 记录：
   - 导入任务 id
   - 导入进度
   - 导入完成状态

导入完成后的通过标准：

- 页面重新检查服务时，`friend_messages > 0`
- `response_pairs > 0`
- 至少一种记忆统计不再是空库

#### 阶段 5：回到首页真实发送消息

1. 打开 `http://localhost:5173/`
2. 确认底部确实存在“说点什么”的真实输入框
3. 用鼠标点击输入框，让焦点真实落在输入框里
4. 输入测试短句
5. 用回车发送
6. 观察聊天区是否真的出现：
   - 用户自己的消息气泡
   - 对方最终回复气泡

如果只出现输入框闪动、但聊天区没有新增消息气泡，这一轮只能记为：

- `发送失败`

不能继续讨论 Afterglow 是否命中记忆。

#### 阶段 6：强命中和弱命中要分开测

建议至少做两轮真实消息测试：

1. 强命中短句
   - 目标：验证导入聊天记录后，向量库真的参与回复
   - 判定：回复明显延续历史语气，但不泄露“我检索到记忆了”
2. 弱命中短句
   - 目标：验证证据不足时不会硬装熟
   - 判定：回复自然，但不过度亲密，也不编造历史

#### 阶段 7：发送后立刻回 Memory 页看观测区

这一步是为了把“页面回复自然”和“Afterglow 方法真的参与了”这两件事同时证明出来。

1. 发送完成后回到 `settings/memory`
2. 查看 `Afterglow 验收观测`
3. 记录：
   - 检索调试输入
   - `memory/search` 结果
   - `debug/stats.model_chain`
   - `writeback` 统计
4. 如果聊天页回复看起来正常，但这里仍然显示：
   - 空的 `model_chain`
   - 空的检索结果
   - 记忆库统计没有变化
5. 则不能直接宣称 Afterglow 已真实发挥作用

#### 阶段 8：再去观测 prompt 与最终回复

为了回答“拼接了哪些 prompt、最终 prompt 是什么”，发送后还要补抓：

1. AIRI 的 context observability / prompt projection
2. 当前 provider
3. 当前 model
4. 用户输入原文
5. 最终发给 provider 的 prompt 段落结构
6. 页面上的最终用户可见回复

最终报告必须同时包含：

- 页面上真实发了什么
- 页面上真实回了什么
- 中间用了哪些 prompt 片段
- 最终 prompt 长什么样
- 是否真的有向量记忆参与
- 是否出现“检索 / 向量库 / prompt / system”泄露

### 11.5.5 基于这次联调的失败判定速查表

为了减少误判，可以直接按下面口径归类：

- 页面里有值，但“检查 Afterglow 服务”失败：优先怀疑 token 已过期或页面保存的是旧 key
- `运行时 API` 已就绪但 `配置向导` 未就绪：说明只能访问后端，不能证明导入和检索链已可用
- `wizard_completed = false`：禁止宣称真实 Afterglow 聊天链路已完成
- 首页消息发送后没有消息气泡：记为 `发送失败`
- 当前 provider 不是 `afterglow`：记为 `链路失败`
- provider 是 `afterglow` 但 `memory/search`、`model_chain`、向量库统计都没有证据：记为 `方法失败`
- 回复虽然自然，但出现“我从记忆里找到了”“我检索到上下文了”：记为 `体验失败`

### 11.6 基于本次联调经验的具体注意事项

这次联调已经暴露出几个容易误判的问题，后续测试时应显式检查：

- 输入框“看起来提交了”，不代表消息真的发出过
- 页面上选中了 Afterglow，不代表当前回合实际走的是 Afterglow
- 本地 `.env.local` 里有 `AFTERGLOW_*`，不代表浏览器端 `import.meta.env.AFTERGLOW_*` 一定可用
- 看到命中记忆的内容，不代表回复样式就是正确的
- mock backend 可能证明“检索链路通了”，但不能证明“正式体验对了”
- 左下角调试面板这类临时 UI 可能污染对产品体验的判断

### 11.7 推荐的浏览器验证顺序

为了减少误判，建议每次都按这个顺序测试：

1. 先测“能不能真实发送”
2. 再测“是不是走了 Afterglow provider”
3. 再测“导入记忆有没有参与”
4. 最后测“用户看到的回复是否自然”

这个顺序的好处是：

- 先排除输入链路问题
- 再排除 provider 配置假生效
- 再排除记忆未实际参与
- 最后才判断体验质量

### 11.8 通过与失败的判定口径

可以把一次浏览器联调回合分成四档：

- `发送失败`：输入框行为异常，消息未真正进入链路
- `链路失败`：消息发出，但没有走 Afterglow 或 provider / model 错误
- `方法失败`：走了 Afterglow，但记忆 / 向量库 / continuity 没有实际发挥作用
- `体验失败`：方法生效了，但用户看到的是解释型、系统型、不自然的回复

只有同时满足下面三点，才算真正通过：

- 真实浏览器路径发送成功
- Afterglow 方法链路生效
- 用户回复体验正确

## 12. 示例对比

### 不合格

用户：

`啵啵爱你`

回复：

`我从导入记忆里找到了相关上下文：user:好嘟！ | assistant:亲亲贝贝右脸蛋！`

问题：

- 泄露了检索机制
- 回复对象从“角色”变成了“系统”
- 把样例展示错当成了自然接话

### 合格

用户：

`啵啵爱你`

回复：

`好嘟`

或：

`亲亲`

或：

`你今天怎么这么甜`

原因：

- 用户只感知到关系延续
- 风格来自记忆，但记忆本身没有被解释出来
- 角色感比系统感强
